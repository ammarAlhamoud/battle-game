# Local saves and progression

The browser uses IndexedDB database `eightfold-saves`, schema version 1, with a `snapshots` object store. A save validates and detaches the complete state immediately, then serializes writes in invocation order. One read/write transaction moves the previous valid `current` snapshot to `previous` and writes the new `current`. An interrupted transaction leaves the prior committed state intact. An invalid current snapshot never replaces a good backup. Loading validates current first and falls back to the previous committed valid snapshot; if both are invalid it reports an error instead of silently resetting progress. Browser storage errors remain visible to the integration layer. Close other game tabs if an IndexedDB schema upgrade is blocked.

Save format version 1 contains the timestamp, campaign, and optional full active `BattleState`. The battle includes mission/seed, both factions, every unit and its facing/status/orders/route/cooldowns, production lines and their queues/blocked state, reserves in priority order, stronghold control/capture, constructed defenses, both fog grids and memories, both AI plans, transient events, simulation time/tick, deterministic ID cursor, pause/result state and AI-side configuration. Maps are immutable versioned mission content, so the mission ID and seed restore the resolved authored map. The version validator rejects other schema versions; future migrations must be explicit rather than interpreting incompatible state.

Export produces an ordinary portable JSON file. Import accepts a nonempty file up to 16 MiB, parses JSON, and applies the same strict runtime validation as normal save/load. It verifies all required fields, finite/ranged values, array limits, matching map/fog dimensions, legal current-era unit definitions, immutable mission strongholds, unique entity IDs, valid queues, every skill prerequisite, and progression accounting. Import validation returns a detached snapshot and does not replace a save before the caller explicitly commits it.

Campaigns start with 3 skill points. A skill purchase subtracts its declared cost and is available only between missions, after prerequisites and the associated era are unlocked. Respec refunds all declared costs and consumes 1 permanent skill point; `totalEarned` stores the net earned balance after these fees. Its conservation rule is `available points + purchased skill costs = totalEarned`, and total earnings cannot exceed the initial grant plus claimed mission thresholds.

The simulation calculates the score. Kill points diminish per repeated enemy type (`round(cost × 3 / sqrt(1 + (previous same-type kills)/3))`), without diminishing resource rewards. First captures, army preservation, military/economic efficiency and victory/tempo contribute separate bounded or one-time bonuses. Persistence uses the final integer score directly and never adds these bonuses a second time. Each threshold grants one skill point and is recorded by its zero-based index. Victory may claim every newly attained threshold. Defeat evaluates half the actual score and may claim only the first two thresholds. This provides genuine partial progress while capping intentional repeat-loss rewards. Winning unlocks the next ordered mission, including the next era after the finale. Replays preserve all prior victories and best scores.

Threshold rewards form a unique ordered prefix per mission. Applying the same result repeatedly cannot add points. A later improved score can claim only the newly reached thresholds. A defeat cannot unlock a mission or claim victory-only threshold indices. Validation rejects duplicate reward entries, rewards above the recorded performance, progress beyond a locked mission, unearned point balances and illegal skills. The complete campaign ledger and battle are committed together, so a reload cannot commit one without the other.

This is a local, single-player game without server accounts or cryptographic authority. Validation prevents malformed/corrupt saves and accidental duplicate rewards; it cannot prove that a deliberately edited but internally consistent JSON file represents honest gameplay. Importing an older valid export intentionally rolls back the entire local campaign; it does not merge rewards from multiple timelines. Clearing site storage removes local saves, so export before clearing browser data or changing hosting origin.

## Verification

`npm test` includes 14 focused progression/save tests, including live snapshots from all 40 authored missions, exact continuation after saving/restoring a running AI battle, the complete eight-era mission-unlock/reward sequence, skill/respec rules, bounded loss rewards, duplicate claims, malformed imports and invalid state references.

Run `npm run dev`, then `node scripts/qa-storage.mjs` (or pass the development-server URL). The script launches Chromium in a fresh isolated browser context and never touches the user's ordinary browser data. Set `CHROMIUM_PATH` if Chromium is installed outside Playwright's cache or `/usr/bin/chromium`.

The storage script passed in headless Chromium 154 on Linux on 2026-10-18. Its live paused battle export was 55,248 bytes with eight soldiers. It verified complete IndexedDB round trips, transactional current/previous commits, recovery after deliberately corrupting current, preservation of the valid backup when saving after corruption, explicit transaction-abort rollback, portable export/import, ordered simultaneous saves, invalid-reward-ledger rejection without changing committed records, and an explicit error when both snapshots are corrupt. These storage checks use the Vite development origin; the production application's full gameplay/offline browser checks are reported separately.
